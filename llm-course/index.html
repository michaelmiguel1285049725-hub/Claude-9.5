1.1

没有老师，怎么给机器出几万亿道题？

——为什么偏偏选"预测下一个词"这个任务，而不是直接教它知识

为什么必须这样

先想清楚"训练"需要什么。机器学东西的办法其实很笨：给它一道题，它作答；对照标准答案，答得不好，就把它内部的"旋钮"拧一点点。每次只拧一点点，所以这个"做题—对答案—拧旋钮"的循环要重复极多次，多到几万亿次。

这样一来，真正卡脖子的就不是"教什么"，而是：几万亿道带标准答案的题，从哪来？

你手里有人类写下的海量文字，但没有老师，也没有答案册。摆在面前的是两条路。拖动下面的滑块，看看每条路要付出什么。

实验台 ① 两条路的账

拖动滑块，改变想要的题数

路线 A · 请人出题

问：法国的首都是哪里？ 答：巴黎
—

假设一个人每 30 秒写出一道题、一年工作 2000 小时，也就是每人每年 24 万道。还没算"谁来判定答案对不对"。

路线 B · 遮住下一个词

题：法国的首都是 ▢　答：巴黎（原文写着）
0 人工

任何一段现成文字，在任意位置切一刀：前面是题，后面那个词就是答案。只需要有这么多文字。

参照：Meta 公开说 Llama 3 用了超过 15 万亿个 token 训练（token 是什么，1.3 节讲；先把它当作"一个词"）。滑块最右端就是这个量级。

路线 B 的"切一刀"具体长什么样？挑一段文字，一格一格往后推：

按"下一道题"，或直接拖滑块
题目 答案

推出来的

路线 B 赢在两件事：答案是文字自带的，不用任何人标注，也不用争论对错——原文写什么，什么就是答案；任何文字、任何位置都能出题，诗、财报、代码都行，题量只受文字总量限制。

所以"预测下一个词"被选中，并不是因为它最像"学知识"，而是因为在"没有老师"的条件下，只有它能把人类现成的文字变成几万亿道有标准答案的题。

机制

一道题从出题到"拧旋钮"，完整走一遍是这样的。点每一步看细节：

实验台 ③ 一道题的一生

点步骤，或拖下面的训练进度

给正确答案"巴黎"的概率 这道题扣分

扣分 = −log₂(给正确答案的概率)。给 100% 扣 0 分；给 50% 扣 1 分；25% 扣 2 分——每少一半，多扣 1 分。训练的全部目标，就是让所有题的扣分加起来尽量小。图中数字为示意。

注意第 ② 步：模型交出的是一张概率表，不是一个词。为什么是表？是谁从表里挑出最终那个词的？——这是第 2 讲的起点。

连到你

你做过推荐系统的语义召回。推荐模型的训练样本里，"答案"通常不是人标的，而是用户自己的行为：点没点、看没看完、买没买。没人逐条去标"这个用户喜欢这条内容"。按你给的线索推测，待你校对

这和路线 B 是同一招：挑一个答案天然长在数据里的任务，才喂得起海量样本。大模型只是把这招用在了文字上——每段文字的"下一个词"，就是一份现成的、免费的行为日志。

1.2

只让它填空，它怎么学会了知识和推理？

——为什么说知识和推理是"副产品"

为什么必须这样

训练目标里只有一句话：把原文真实的下一个词的概率抬高（也就是把扣分压低）。没有一个字提到"知识"或"推理"。

可训练出来的模型能答事实、能算数、能做简单推理。这些本事是从哪来的？动手试：下面五个空都是语料里随处可见的那种句子。给模型开关不同的能力，看它在每个空上扣多少分。

实验台 ④ 给模型装能力

勾选能力，看每个空的概率表怎么变
五个空的总扣分
— 给正确答案的平均概率
—

概率为示意数字，用来展示"哪种能力影响哪个空"，不是某个真实模型的输出。

推出来的

每种能力只在需要它的那几个空上降低扣分。而训练要压低的是所有文字上的总扣分——文字里什么样的空都有：要常识的、要算数的、要推理的。所以谁能把扣分压下去，谁就会被一点点"拧"出来。

知识和推理从来不是训练目标，而是为了把空填对，不得不长出来的副产品。

再看第 1 个空：所有能力全开，"苹果"也只有约四分之一。原文本来就有多种合理写法，再强的模型也只能分概率——这是扣分永远降不到 0 的原因之一。

机制

还有一个疑问：想填对空，最省事的办法难道不是把读过的句子全背下来？

算笔账。Llama 3 训练用了超过 15 万亿个 token，它当时最大的版本有 700 亿个参数（就是"旋钮"）。平摊下来，一个旋钮要负责两百多个 token——背是背不下的。装不下，就只能找一条能同时解释很多句子的规律。下面用一个小例子看"背"和"找规律"的成本差多少。

实验台 ⑤ 背下来 vs 找规律

按"多读 10 句"，看两种存法的成本
背诵法：每个不同的句子存一份
规律法：存"国家—首都"事实 + 句式

单位：存下来的字数。

规律法的额外红利

0 句没读过、但规律法能写出来的句子——比如读过"日本的首都是东京"和"我去过法国的首都巴黎"，就能写出"我去过日本的首都东京"。

推出来的

规律比句子少得多，还能推到没见过的组合上。在旋钮有限的条件下，训练会自动偏向这种"一条管很多句"的存法。"法国—首都—巴黎"这样的事实，"A 比 B 高、B 比 C 高"这样的推理套路，本质上都是这种能压缩很多句子的规律。

连到你

拿你熟悉的财报场景说。模型会算"同比"，不是因为谁教过它公式，而是它读过海量"营收 X 亿，同比增长 Y%"的句子，为了猜中那个数，被逼着近似学会了这种换算。待你校对：你的场景里是否让模型算过数

"近似"两个字要紧。实验台 ④ 的第 5 个空，能力全开时正确答案 1000 也只有 74%，还有一截给了常见的错误算法 990（1100 × 0.9）。所以在财报问答里，精确计算更适合交给代码或计算工具，让模型负责找数和组织语言，而不是让它"心算"。

1.3

它读的最小单位是什么？为什么不是字？

——token 是什么，为什么 JSON 的括号引号浪费 token

为什么必须这样

回到实验台 ③ 的第 ② 步：模型每一步要给一张固定清单（词表）上的每一项打概率。所以做模型之前得先定下来：清单上放什么？

三个候选方案，各自会撞上什么墙：

方案一：按整词

清单得列出所有词。可中文没有空格，新词、人名、产品名、错别字无穷无尽，清单外的词只能记成"不认识"。

我想吃[不认识]大餐

"饕餮"不在清单里。

撞墙：总有漏网的词

方案二：按单个字（或字节）

清单很小，什么都能拼出来，永远不会"不认识"。但句子被切得很长，而模型每处理一个单位都要完整算一遍。

我想吃饕餮大餐

第 4 讲会看到：长度翻倍，读的成本不止翻倍。

撞墙：太长、太贵

方案三：折中

常见的片段合成一个单位，少见的拆回小块。那问题来了：哪些该合？——不靠人定，靠数频率。

我想吃饕餮大餐

常见的"大餐"合一个，少见的"饕餮"拆开。

下面动手看它怎么"数"出来

实验台 ⑥ 从频率里长出词表

拖滑块：合并规则一条条加上去

规则只有一条：在一小堆财报句子里，找出最常挨在一起的两个片段，把它们合成一个新片段，记进词表；重复。

一句没在语料里出现过的话，被切成：
词表大小 整个语料切成 个 token
学会的合并（按学会的先后）：

往右：词表越大，同一段语料切出来越短。实际分词器在这条曲线上挑一个点，一般是十万到二十万左右的词表。

推出来的

token 就是这样来的：不是人规定的"字"或"词"，而是按频率从语料里统计出来的片段。常见的串（"季度""同比"）合成一个，少见的拆成小块。所以它永远不会"不认识"，最多是"拆得碎"。

机制

真实分词器的最底层不是"字"，是字节：一个常用汉字存进电脑占 3 个字节。分词器从字节开始合并。如果它统计的语料里中文少，很多汉字就合并不完整，一个字会被拆成 2~3 个 token。

现在能回答"为什么 JSON 浪费 token"了。同一张表（虚构的示例数据），换四种写法，用 o200k 数一数。每个 token 按用途上色：

实验台 ⑧ 同一张表的四种写法

点一行，看它具体被切成什么
真正的内容（数值）键名 / 表头结构符号：括号、引号、逗号、竖线、缩进空格

一个 token 同时跨两类时，按"内容 > 键名 > 结构"归类。留意数字：1500 被切成 150 | 0，数字是按三位一段切的——这也是模型"心算"不稳的一个原因。

推出来的

四种写法里内容 token 一样多（32 个），差别全在"包装"：JSON 每一行都把四个键名重写一遍，每个文字值还要套引号；缩进的空格也要花 token。Markdown 表只写一次表头，但竖线也要钱；CSV 最省。

包装为什么要紧：每个 token 都要完整计算一遍、按 token 计费；能塞进去的 token 总数有上限（第 4 讲）；让模型输出 JSON 时，每个括号引号都是它一步一步生成的，而输出 token 通常比输入贵好几倍，也更慢。

连到你

你在腾讯把数据做成 Markdown 表喂给模型。从实验台 ⑧ 看，它比缩进版 JSON 少了约 44% 的 token（162 → 91），省下的几乎全是重复的键名。

但也看到了：如果只图省，CSV 更省。Markdown 表的价值不全在省——第 4 讲会看到它的另一面：表头当"锚点"，帮模型在长上下文里找对列。

1.4

那它"知道"的，到底是什么？

——为什么模型"知道"的一切都是统计规律，而不是事实

为什么必须这样

把前三节连起来，问一个问题：整个训练过程中，哪一步出现过"这句话是真的"这个信号？

1.1：答案 = 原文的下一个词。原文写什么，什么就算"对"。
1.2：能力 = 任何能压低扣分的规律。
1.3：连读文字的单位，都是按频率数出来的。

一步都没有。那就值得做个实验：如果语料里错的说法比对的多，会怎样？用一个老谣言："从太空唯一能用肉眼看到的人造建筑是长城。"2003 年杨利伟从太空回来后说，他没有看到长城。

实验台 ⑨ 语料投票

拖动辟谣文章的比例

一个只会"数数"的迷你模型：它读 1000 篇文章，只记"这句前文后面出现过什么、出现几次"。谣言文章写"唯一能看到的是长城"；辟谣文章里有七成会先引用谣言再反驳。

问法一（谣言的说法）
从太空唯一能用肉眼看到的人造建筑是 
事实：这个前提本身是错的
问法二（辟谣的说法）
宇航员说，从太空用肉眼 看到长城
事实：不能
推出来的

把比例拉到 0%、50%、100% 各看一眼：模型给的概率跟着语料里的比例走，不跟着事实走。

更要紧的是：辟谣比例拉到 100%，问法一照样几乎全押"长城"。因为它存的不是"长城看不见"这条事实，而是"这种前文后面常跟什么"。换个问法，就换了一套统计。辟谣文章为了辟谣先引用谣言，反倒给"唯一能看到的人造建筑是 → 长城"又添了一票。

机制

所以模型内部并没有一张"事实表"。和真正的事实表（数据库）并排比一下：

实验台 ⑩ 问数据库 vs 问模型

换一个问题

数据库

每一行都有来源和更新时间；没有这一行，就老实说查不到。

模型

不管问什么，它都交出一张概率表。表"尖不尖"只反映见得多不多。数字为示意。

推出来的

模型里只有"什么样的前文后面常跟什么"：没有出处，没有日期，也没有"查不到"这个选项。表尖，说明这种前文在语料里常见、后文很一致；表平，说明见得少或说法杂——但尖和平都不等于对和错。

"它永远交出一张表、没有'查不到'"——第 3 讲会从这里推出：为什么它会流畅地说错，又为什么不说"我不知道"。

连到你

这就是你在腾讯做 RAG 的根本原因。模型对"某公司某季度营收"的"知道"，只是训练语料里这串字后面常跟过什么数：没有出处，还停在训练截止的那天。

RAG 把真实财报递进上下文，等于把"像不像"的参照物，从"训练时读过的全部文字"换成"眼前这份文件"。但比较方式没变，仍然是"像不像"——所以你遇到的 Q3 答成 Q2，数字明明都在上下文里，它还是配错了。第 3 讲就从这个案例接着推。
